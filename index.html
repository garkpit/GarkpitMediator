One front door for every feature.

A small TypeScript library that turns your app into a list of named Commands and Queries, each with exactly one handler. People can find their way around it. So can AI coding agents, and that is the difference between an app that doubles in size gracefully and one that ties itself in knots.

What it looks like

A feature is a class, a handler and one line.

Each thing your app can do gets a name: a Command if it changes something, a Query if it only reads. You send one to the mediator and it runs the single handler registered for it, wrapped in the rules you have installed for every request.

The caller never knows the handler. Move it, rewrite it, split it: nothing else changes.

TypeScript
import { Command, createMediator, LoggingBehavior, MutexBehavior } from '@garkpit/mediator';

// A feature is a class with a name that says what happens.
class RenameNote extends Command<Note> {
  constructor(readonly id: string, readonly title: string) {
    super();
  }
  // One rename per note at a time. No locking code anywhere else.
  mutexKey() {
    return `note:${this.id}`;
  }
}

// It has exactly one handler.
class RenameNoteHandler {
  async handle(command: RenameNote): Promise<Note> {
    return notes.rename(command.id, command.title);
  }
}

const mediator = createMediator({ behaviors: [new MutexBehavior(), new LoggingBehavior()] });
mediator.register(RenameNote, new RenameNoteHandler());

// A page, a test, a job or an AI agent: everyone comes in through the same door.
const note = await mediator.send(new RenameNote('n1', 'Weekly shop'), { actor: 'priya' });

Why it helps as you grow

Agents do well where there is one obvious place for each thing.

An AI coding agent starts every task knowing nothing about your project. It reads a few files, forms a picture and writes code to fit. Ask it to "let users archive a note" and see where that picture leads.

A typical app, a year in

src/
  routes/
    notes.ts              every notes endpoint, 600 lines
    billing.ts
  services/
    noteService.ts        or does archiving go here?
    auditService.ts       remember to call this
  models/
    note.ts
  utils/
    locks.ts              and this
    helpers.ts

Four reasonable places to put it, three existing styles to copy, and two things to remember to call. Each guess is a chance to drift.

The same app with a mediator

src/features/notes/
  create-note/
  rename-note/
    RenameNote.ts             the request: inputs, lock key, audit record
    RenameNoteHandler.ts      the only code that renames a note
    RenameNote.test.ts        sends it through the real pipeline
  archive-note/               new: copy rename-note/, rename, write the handler
  get-note/
  list-notes/
  index.ts                    one registration line per folder

One answer, the same one every time: a new folder beside its neighbours. Locking, auditing and logging come from the pipeline, so there is nothing to remember.

The app can be listed
The feature folders, and mediator.registeredRequestTypes(), are a complete inventory of what the app does. Finding the code to change is a lookup, not a search.
Shared rules cannot be forgotten
They wrap every request. A new endpoint is locked, audited and logged without anyone, human or model, adding a line.
Small files, small context
A feature is three short files. An agent reads only those, and keeps the rest of its working memory for the task.
The compiler checks the wiring
send returns the type the request declares. A wrong result type is an error the agent sees and fixes itself.

The pipeline

Rules you write once and cannot forget.

Every request passes through the same steps on its way to the handler and on its way back. They are called behaviors. Three come with the library; your own (permissions, rate limits, timing) take a dozen lines.

BehaviorA request opts in withWhat you get
MutexBehaviormutexKey()Two commands on the same thing never run at once. The second is refused straight away; locks are always released.
AuditBehaviorauditInfo()One record of who did what, success or failure, with secrets redacted. A failed write never changes the outcome.
LoggingBehaviornothingOne line per request: its name, whether it worked, how long it took.

## Features go through the mediator

This app uses `@garkpit/mediator` (copied into `packages/mediator`; the full manual is
`packages/mediator/llms-full.txt`). Every feature is one Command (it changes something) or one Query
(it only reads), and each has exactly one handler.

To add or change a feature:

1. Look first. Each feature is a folder at `src/features/<area>/<verb-noun>/`. List them and reuse or
   extend an existing one before creating a new one.
2. A new feature is a new folder with three files. Copy the nearest existing slice and rename:
   - `VerbNoun.ts`: the request class. It `extends Command<Result>` or `extends Query<Result>`, its
     constructor takes typed, already-valid values, and a static `parse(input: unknown)` validates
     untyped input.
   - `VerbNounHandler.ts`: `implements Handler<VerbNoun, Result>`. All the logic lives here. It never
     touches the HTTP request or response.
   - `VerbNoun.test.ts`: sends the request through the real mediator and checks the result.
3. Register it with one line in the area's `index.ts`:
   `mediator.register(VerbNoun, new VerbNounHandler(deps))`.
4. Keep routes thin: parse the input, `mediator.send(request, { actor })`, then `ok(data)` or
   `fail(error)`. A route holds no business logic and never touches the database.

Rules:

- Never call a handler directly, and never call one handler from another. Send a request, or move the
  shared code into a plain function that both handlers import.
- Never write locking, audit or logging code in a handler. A command that must not run twice at once on
  the same thing implements `mutexKey()`. A command that should leave a record implements
  `auditInfo()`. The pipeline does the rest.
- Request class names are unique across the app: the mediator finds handlers by class name.
- Every `send` passes `{ actor }` as its second argument.
- Handlers throw typed errors. One shared function maps errors to error codes; do not map them inside
  a route.
- A Query never changes anything. If it does, it is a Command.
- Run `bun run check` before saying the work is done.

The agentic interface

Then let AI use the app, through the same door.

Everything your app can do is already a list of named, typed requests. That is almost exactly what a model needs to use a tool. Describe each one once and the app gains two new doors: a chat assistant inside it, and an MCP endpoint for agents outside it.

Self-aware
The app can describe what it can do. An agent that connects asks for the list; it does not scrape pages or wait to be told.
Self-maintaining
Agents can run day-to-day operations safely, because every action goes through the one audited door. Reads run at once. Changes wait for a person to confirm.
Honest about it
The app does not rewrite itself or run without people. One test compares the tool list with what the mediator has registered, so a feature can never be half added. Read how to build both doors

Read this before you adopt it.

Small things done plainly. These are the edges.

No npm package
You copy the source into your project and note the commit. Nothing changes underneath you; taking a newer version is your decision.
Locks are per process
The built-in lock lives in memory. It does not coordinate across several servers. For that, write a behavior that takes the lock from your database.
Class names matter
Handlers are found by class name, which keeps hot reload working. A minifier must not rename classes in a server bundle.
It stays small
No dependency injection container, no events, no validation library, no queues. One request, one handler, one pipeline.
No support
A personal project shared as it is, under the MIT licence. Not a product of, or endorsed by, any employer.
